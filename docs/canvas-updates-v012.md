# 0.12 動態電視與 InBody 畫面更新

這次保留原本的電視畫面、文字、768×432 尺寸、貼圖設定與名義 12 Hz 動畫。渲染前才依最終相機判斷螢幕是否在視錐內、祖先是否可見，以及電視正面是否朝向相機。電視後面有完整的不透明外殼，從背面看不到顯示面；這項背面判斷只套用於電視，沒有把其他雙面材質一併裁掉。

看不到的電視不再重畫 Canvas。回到視野時，直接使用目前全域播放時間畫出該格，沒有補播離開期間的歷史畫格，也沒有讓影片時間重新開始。同一 12 Hz 畫格內多次渲染不會重複要求更新。這裡只做保守的視錐與背面判斷，沒有新增昂貴的全場景遮擋光線檢查。

`architecture.prepareRender(camera)` 應在最終相機、房間顯示狀態確定後，且在 `renderer.render()` 前呼叫。沒有要渲染的模擬更新不畫電視。

InBody 維持原本 640×400 畫面和八秒示範進度。閒置或完成後內容不變時，不再重畫和設定 `texture.needsUpdate`。開始、結束立刻更新畫面；掃描期間仍使用精確進度畫進度條，沒有因為百分比文字相同而把進度條取整。原有「固定範例，非玩家量測」文字和回傳結果保留。

## 診斷與驗證

- `getFacilityDiagnostics().canvasUpdates.sports` 回報實際重畫／更新要求、略過的隱藏畫面，以及各螢幕最後顯示的全域時間。
- `getFacilityDiagnostics().inbody.canvas` 回報實際重畫、跳過的相同狀態及目前畫面鍵。
- 舊的 `screenFrames` 仍表示邏輯播放時間，不能拿它當成實際重畫次數。
- 純 Node 的[七項測試](../tests/canvas-updates-v012.test.mjs)通過，涵蓋可見節奏、畫格去重、轉向／父層可見性、離開與重入，以及 InBody 開始、掃描、完成、結束。
- [CPU 對照報告](../artifacts/canvas-updates-v012/cpu-qualification.json)使用更新前快照與目前真正的場館建構程式。初始畫面、可見電視在相同二十秒時點的畫圖指令、InBody 掃描及完成畫圖指令完全相同；場館幾何建構參數、碰撞資料及設施碰撞體積也相同。

CPU 固定六十次模擬更新下，十秒內三張不可見電視原各要求更新 106 次，現在均為零。這是 Canvas 重畫及 `needsUpdate` 要求，**不是實際 GL 上傳數量或 GPU bytes**；Three 本來就可能不替視錐外的 mesh 上傳貼圖。[實際遊玩測量](performance-v012.md)另比較遊戲 RAF 間隔，沒有由更新要求推算 GL 傳輸量。

新排程器採全域時間的十二分之一秒畫格。舊的 `elapsed - lastScreenTime > 1/12` 在固定 60 Hz 模擬下因嚴格時間門檻，實際約 10.6 Hz；新排程器在可見時穩定採用名義 12 Hz。它沒有靠降低可見電視的畫面更新率來減少負載。
